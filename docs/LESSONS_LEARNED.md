# 独立经验记录

本记录可单独阅读和保留，来自 Mac 2.5.0 → 11英寸 iPad Pro M5 / iPadOS27.0.1 的实际试错。

## 先证明哪一层工作

彩色三角形和触控变色只验证了窗口、Metal和UIKit桥接。它们不能证明游戏初始化、资源完整、引擎接口或存档可用。早期游戏壳闪退时，应把启动日志、退出路径、资源访问、扩展签名逐项隔离，直到完整资源导入后进入真实场景。

Mac与iPad同为ARM64，CPU代码可沿用，但平台标签、AppKit窗口、事件循环、文件位置和权限仍需适配。优先复用已成功的相同游戏案例，固定上游commit、SDK、宿主hash和每次改动范围。

## 输入问题需要把计时边界拆开

v8的UIControl回调选择器写错，造成画面有按键却无输入。v9修正后能通过启动提示，但手感仍差。v11搬入塞尔达式单UIView和完整布局编辑器，仍出现归零和延迟。

v12发现安全区变化、重复物理手柄通知不应无条件清空手指。保留真实后台、布局编辑、取消、尺寸改变和物理接管的释放路径。持续按住不归零后，用户仍报告滞后和漏识别。

旧age-ms在发布游戏回调之后记录，混合了送达等待和处理耗时。v13改为入口年龄、发布耗时、回调总耗时、更新/绘制序号分别计时。兼容层在游戏轮询处有界处理已就绪UIKit来源，脏控件显式提交。用户确认圆点明显跟手且短按正常。

不要把CPU回调预算当成严格的端到端延迟保证。2ms预算是在回调之间检查，无法抢占一个本身耗时很长的回调。不同测试阶段与计时定义的统计不能直接算性能提升百分比。

## 体感接入与手感验收分别记录

体感映射右摇杆会经过游戏自己的死区、横纵灵敏度和转向曲线。用户反馈左右不均、横纵不同，而手指右摇杆正常。v14的重力投影会在斜握时把俯仰混进yaw，宽松校准还可能把真实缓慢转动学成零点偏差。

v15让yaw/pitch正交，严格限制稳定小偏置，使用按采样时间的轻度滤波，并加横纵倍率。96条C断言覆盖这些问题的复现与修正。后续还需单独验收方向一致性，静态测试不能替代手感。

传感器请求120Hz，游戏可能约30次/秒消费最新样本。应报告消费频率和游戏实帧，避免把屏幕120Hz或采样请求值当作实际视角更新率。

## 分辨率至少有三个尺寸

逻辑窗口点数、显示纹理像素、超分内部渲染尺寸分别检查。此前MetalFX HUD记录内部786×542、输出1210×834，输出恰为面板2420×1668的一半。兼容层只枚举单个半尺寸模式，是菜单固定低分辨率的直接线索。

v16先用1920×1324验证，v17/v17b扩成多档。菜单出现选项后仍要读取drawable或HUD，确认引擎真正采用它。本次HDR验收时实际drawable为1815×1251，不应写成已实测原生全屏分辨率。

## HDR不能靠一个开关或菜单判断

v18把NSScreen的固定SDR值接到UIScreen EDR查询，设备日志确认potential=16、current约1.20。游戏没有HDR开关、创建图层时wants=0，这两点都不足以单独证明最终状态。Mac原版使用自动校准EDR，创建日志也早于引擎配置完成。

v19在实际nextDrawable处采样，确认EDR关闭、格式80和sRGB。调低亮度后仍为SDR，排除了这次简单亮度对照能触发HDR的假设。v20由宿主申请EDR，创建时wants=1，但实际27次采样仍全部为SDR，因此单独申请EDR未解决问题。

继续只读追查游戏调用，发现它先确认potential>1，随后查询Mac专属旧Metal功能集10001。SDK将其定义为macOS_GPUFamily1_v2。该HDR模式枚举判断返回不支持时只保留SDR。

v21把兼容处理限定在已核对执行文件的这一个HDR查询返回位置，先验证原生Metal4、Apple9及RGBA16Float纹理创建。实机确认原查询native=0，范围命中，兼容result=1。游戏随后自行选择格式115、PQ色彩空间、wants=1，39个出帧样本一致，用户也反馈成功。

经验是从能力枚举追到引擎模式选择，再追到真实显示纹理。给8位SDR画面加开关或提高亮度无法替代HDR渲染。该兼容映射仅用于已核对查询，不是整个旧Mac功能集的通用符合性声明。游戏版本变化必须重新核对hash和调用位置。

## 分体资源、真实签名和恢复边界

约79.7GB资源只导入一次，小型程序更新通过同标识覆盖。先备份存档/偏好，再安装，随后核对资源清单和存档。完整资源不应每次塞进更新IPA。

ExtensionKit父包和Background Assets子包分别需要真实profile，App Group要对应实际分配结果。签名成功和安装成功分别验证。合成签名测试只证明数学、资源封印和错误拒绝行为，最终信任与权限由设备判断。

GetMoreRAM的多轮登录失败记录提供了旁证，成功路线使用扩展适配的iLoader。私有检查点包含profile、设备标识和签名包，只能私下保存。公开档案应根据白名单重新构造证据，避免直接复制原始日志再逐行打码。

## USB故障要区分层次

资源管理器能看到照片，不代表Apple安装/应用容器数据通道正常。此次左侧USB4曾在游戏前台出现连接问题，右侧USB-C可用。原因没有最终确定，不能归因于游戏功耗或某个驱动。用户回主屏保留游戏后台后读取本地日志，是本项目可用的诊断方式。

## 发布时固定可以证明的结果

保存最终源码、纯模块hash、宿主hash、版本约束和脱敏验收表。失败假设也应保存。HDR路径启用、色彩准确、1600nit峰值、持续性能和插帧可用性是不同的验证项目。本次只把已有证据覆盖的项目写为通过。
